  Your question: frontend first, or both lines in parallel?

  In the AI era I recommend contract first, then build both sides in parallel 
  against the contract. You shouldn't fully finish the frontend before starting
  the backend, and you shouldn't start both blind either.

  1. Days 1–2: fix the contract.
     - Turn the interfaces in the diagram into an OpenAPI file (or a Postman
       collection).
     - Everyone reviews it together, then you freeze it.
     - This step can't be skipped. AI writes code fast, but if the contract
       isn't agreed, two AIs will each write their own version and they won't
       fit together.
  2. Days 2–3: the frontend builds a clickable prototype against mock data.
     - Use the OpenAPI file to spin up a mock server.
     - The frontend takes AI's help and builds all 5 pages, so the flow can be
       clicked end to end.
     - The real use of this prototype is to put it in front of the team or users
       and find gaps in the design. When you find one, change the contract;
       it's cheapest at this point.
  3. From day 3: the backend fills in the real implementation behind the same 
     contract.
     - Split by module: Auth, Quote, Order + state machine, Tracking +
       simulator.
     - Each person brings their module up to the contract.
     - As each module is done, switch the frontend from mock to the real API.

  Why not build the frontend first and then the backend together? AI makes the
  frontend fast, but without a backend the frontend gets written against made-up
  data structures, and you have to rework it when integrating. And why not run
  both lines blind? That's what makes integration hurt. With a contract in
  place, the two lines don't wait on each other, and AI can generate code
  straight from the contract: types, mocks, Controller skeletons, tests.

  One thing to note: the frontend only needs 1 person. The prototype can be done
  in 2–3 days. The backend is where the work is, especially the ordering
  transaction and tracking. Put more people there.

● 这几个决定都已经写进前端、后端、数据库三张结构图和 ⧉ 设计总览，链接没变。

  设备随时接单（你理解得对）
  - 每台设备的时间表存在 device_block
    表里。每单占两段：从出发到送达一段，返航一段。
  - 设备的最早空闲时间，就是它最后一段占用结束的时间。
  - 报价时，每个方案都返回最早出发时间。设备空着就显示 Now，忙的话显示类似 “Next
    free 3:40 PM”，预计到达时间里已经算上了等待。
  - 下单时，新订单接在该设备最后一段占用之后。订单表新增出发时间字段
    departs_at。

  定价
  - 价格 = 重量 kg × 取件到收件的英里数 × $1，机器人和无人机同价。
  - 重量改成直接存 kg（weight_kg），不再用重量档位。
  - 这个参数放在配置里，以后可以随时改。
  - 按这个公式会出现两个情况：
    - 很轻、很近的单只要几美分。例如 0.3 kg 走 0.5 英里，是
      $0.15。要不要加个最低价，比如 $1，你定。
    - 机器人走路网，距离比无人机的直线长，所以同一单机器人会稍贵一点。

  取消订单
  - 只能在设备出发前取消。例如预约 1 小时后出发，这 1
    小时内都可以取消；出发后取消按钮就隐藏，后端也会拒绝。
  - 取消时释放这一单的两段占用。排在它后面的订单不会自动提前，这样处理最简单。

  时区
  - 所有时间都按美西时间（America/Los_Angeles）显示。数据库按 UTC
    存，前端用一个工具文件统一转换格式。

  目前只剩一个点没定：演示时要不要预置测试账号和几笔已完成的订单。另外上面的最低
  价也请你定一下。
